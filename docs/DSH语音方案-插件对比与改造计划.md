# DSH 语音方案：插件对比、架构方向与后续改造计划

> 本文档整理自 2026-08-31 讨论，汇总两个 DSH 语音插件（`dsh-voice-mode` 与 `dsh-voco`）的对比结论、已确定的架构方向，以及基于 `dsh-voco` 的后续改造计划。

---

## 1. 插件对比

### 1.1 概览

| 维度 | `dsh-voice-mode` | `dsh-voco` |
| --- | --- | --- |
| 仓库 | [qishuilalala/dsh-voice-mode](https://github.com/qishuilalala/dsh-voice-mode) | [lgquan/dsh-voco](https://github.com/lgquan/dsh-voco) |
| 版本 | v0.6.0 | v0.3.10 |
| 定位 | 会话内全双工语音对话 | 持久语音会话 + 后台 Agent 委派 |
| 语音识别 | 本地推理（zipformer2 流式 + SenseVoice 定稿），零 API Key | 云端识别（硅基流动 XingChenASR-V3.2-Ultra，需 API Key） |
| 语音朗读 | 默认 Edge 云端；本地 VITS / Kokoro 可选 | Edge TTS |
| 会话架构 | **合一**：语音直接进当前会话，Agent 在同一会话内干活 | **分离**：语音主会话 + 后台 Agent 子会话委派 |
| 上下文机制 | 复用 DSH 会话本身，无自研记忆层 | 显式处理：任务重述、工作状态交接、可选 workspace-memory |
| 成熟度 | 较高（文档 / ADR / CI / 测试齐全，进 awesome-dsh-plugin） | 较新但活跃（121 commits） |

### 1.2 `dsh-voice-mode` 特点

- **真·全双工**：一边说一边实时出字（流式识别），停顿约 700ms 自动发送；AI 朗读时开口即打断（barge-in）
- **两种交互模式**：`toggle`（持续聆听自动断句）/ `hold`（按住说话、松手即发）
- **本地识别 + 本地 TTS 可选**：隐私优先、无需 API Key、可离线使用
- 工程完备：架构图、ADR 决策记录、CI、单元测试、中英文文档

**优点**
- 交互体验打磨极致，像打电话一样自然（按句朗读、实时字幕、开口打断）
- 隐私好：识别本地推理，朗读可选本地 VITS/Kokoro，回复文本不出本机
- 短期会话连贯性最好：语音内容直接进当前会话，Agent 能看到完整历史，无需任何传递机制

**缺点**
- 无自研记忆 / 上下文管理层，跨会话记忆完全依赖 DSH 本身
- 语音转写、工具日志、reasoning 全部挤在同一上下文窗口，长对话触发轮换时早期内容被挤出
- 无法并行分派多个子 Agent，一次只能处理一个任务流
- 本地小模型识别准确率低于云端大模型

### 1.3 `dsh-voco` 特点

- **语音主会话 + 委派后台 Agent 子会话**（`parentSession` / `origin: 'subagent'` 子会话收纳）
- 普通聊天前台直接处理；需要工具 / 项目工作委派给后台 Agent，语音只播报简洁结果，完整报告留档在任务界面
- 委派前做**带上下文的任务重述**（省略指代重写为自包含任务，前置背景与用户原话分开传给后台），防止子 Agent "失忆"
- 子会话策略：`isolated`（每次委派新建）/ `continuous`（模型一致且上下文压力未达软高水位时复用当前子会话）；压力达到阈值或 token 预算不足时，在任务边界创建新子会话并**注入有限的工作状态交接**（不盲目复制历史）
- 可选集成 workspace-memory：语音主会话与每个完成的委派子任务进入同一长期记忆范围
- 支持打断、断线重连、历史恢复，绑定关系在重连 / 重启后恢复

**优点**
- 上下文干净：语音闲聊不污染任务上下文，窗口利用率高
- 长期记忆 + 可追溯：完整报告留档，可回顾、可复核
- 灵活性：一个语音主会话可并行分派多个子 Agent，各自独立上下文，可同时开工、统一汇报
- 契合"语音派活 + 后台长任务 + 人工把关"的使用方式

**缺点**
- 成熟度不如前者（新项目、社区关注度低）
- 依赖云端识别：需 API Key、依赖网络
- 分离架构有上下文衔接成本，需靠重述 / 交接 / 记忆机制补偿（voco 已实现，需持续保持）

### 1.4 关键结论

- **速度打平**：两者的耗时大头都在模型推理与工具调用，架构差异对整体时长影响很小，速度不构成选择依据
- **真正的差异在架构**：合一（实时对话优先） vs 分离（语音遥控 + 后台委派）
- **场景建议**
  - 想要"像打电话一样实时对话、隐私优先、不配 Key" → 选 `dsh-voice-mode`
  - 想要"语音遥控 Agent 干重活、结果留档可追溯、支持并行多 Agent" → 选 `dsh-voco`
- **结论**：`dsh-voco` 的委派 / 分离方向与"语音指挥 Agent 干活"的目标更贴合

## 2. 架构方向：坚持分离架构

### 2.1 为什么坚持分离

- **速度不是理由**（两者打平），分离的价值在架构层面，而非性能
- 分离架构的核心优势：
  1. **可并行分派**：一个语音主会话可以同时派多个子 Agent，各自有独立上下文、互不干扰，一次指令让多个 Agent 同时开工再统一汇报
  2. **主会话轻量**：语音主会话只负责听懂指令、调度、播报结果；重活全在后台子会话跑，语音聊天不被工具日志和长任务拖着
  3. **记忆沉淀**：结合 workspace-memory，多个任务的成果沉淀进同一长期记忆，形成知识积累，随口一问还能想起
  4. **契合多 Agent 工作流**：与"临床试验入组筛查系统"这类四 Agent 工作流（方案解析 / 病历提取 / 匹配判断 / 最终决策）天然契合——语音当指挥台，一句话分派多个 Agent 并行干活再汇总
- 外部印证：ChatGPT 也建议"语音与文本会话分离"，与 voco 的设计思路一致

### 2.2 分离架构必须处理的坑

- **上下文衔接**：子 Agent 是全新上下文，不知道之前聊过什么，必须靠"任务重述"把背景带过去（voco 已有此机制，需保持并持续强化）
- **多 Agent 并行后的结果汇聚与记忆协调**：多个 Agent 各干各的，如何把成果整理好、不冲突地写入同一记忆，需要专门设计

## 3. 后续改造计划

### 3.1 (a) 语音的改造：主会话任务进度面板 + 审批面板

**需求背景**

当前系统委派 Agent 任务时，无法在语音主会话中看到执行进度。希望在语音会话中增加一个小面板（方框）：

1. **查看子 Agent（子会话）的任务完成进度**
2. **子 Agent 内部有审批情况时，在主会话中直接浏览并审批**

做成功后，可以用语音控制做很多重任务，包括语音控制 Agent 写代码，并保留人工把关。

**可行性：DSH 原生能力充分支撑**

- **进度**：DSH 提供
  - 子代理生命周期事件：`subagent/start`、`subagent/end`
  - `subagentTiming` 投影：累加 `turn/start` → `turn/end` 活跃时间，可提供 `active.since` / `active.through`
  - `listChildren()` / `listDescendants()`：枚举子代理（`running` / `inactive`、持久化标签、层级深度），不加载不恢复
  - 会话事件流：`step/start`、`step/end`、`todo/write`、`tool/call`、`tool/result` —— 进度栏想要多细都行
- **审批**：DSH 有 approval seam（`ctx.approval.request`；`approval/request` waterfall 应答者；结果词汇 `allowed-once` / `rejected` / `cancelled` / `unavailable`；审计事件 `approval/asked`、`approval/decided`）

**关键限制（必须知道）**

DSH 委派策略会**强制子 Agent 的审批策略固定为 `never`**（`captureDelegatedPolicyOverrides`）——被委派的子 Agent 内部一旦请求审批，会被确定性拒绝，**不会等待人处理**。这是刻意的安全设计（防止后台子代理干等无人处理的审批）。因此"主会话审批子 Agent 内部请求"**不能直接用现成 approval seam**，需要换思路。

**两条实现路径**

- **路径一：用 DSH approval seam（需绕过 `never` 固定）**
  - 优点：贴合官方机制
  - 缺点：仅一次性授权（无 allow-always / 记住规则 / 撤销）；请求不携带工具参数（只给工具名、原因、可选调用 id）；无内置应答者需自建；请求只在尚未结束的轮次内有效
- **路径二（推荐）：voco 自研审批协议**
  - 给子 Agent 注入一个"请求人工确认"专用工具
  - 子 Agent 在关键节点调用该工具（执行危险命令、关键决策前）
  - 请求通过事件回传主会话 → 小面板弹出审批框 → 用户批准 / 拒绝 → 通过 `followup` 把决定发回子 Agent 继续执行
  - 优点：完全可控，可携带上下文、可记住规则、可批量审批，不受官方 `never` 限制

**进度面板落点**

订阅子会话的 `step` / `todo` / `tool` 事件，在主会话内渲染为一个小卡片；结合 `subagentTiming` 投影与 `listChildren` 的 running 状态，实现"正在跑哪些子任务、各到什么阶段"的实时视图。

### 3.2 (b) 流式输出的改造：按句朗读 + 实时字幕 + 开口打断

**现状**

`dsh-voco` 使用 Edge TTS 播报简洁结果，一次合成整体朗读。

**目标（参考 `dsh-voice-mode` 的交互体验）**

- **按句朗读**：只读最终答复，跳过 reasoning / 工具调用
- **实时字幕跟随**：字幕随播放滚动，可跳过当前句
- **开口即打断（barge-in）**：AI 朗读时开口说话 → 朗读即刻停止、你的话被听见
- **声学打断引擎**：自适应阈值（滚动噪声地板），朗读时自动超灵敏，外放也能精准打断、不误伤自己；本地静音 + 合成队列作废 + 正在运行的回合取消

> 参考细节（dsh-voice-mode 已实现）：打断延迟约 525ms（VAD 0.35 + 泄漏计数）；回声消除以浏览器原生 AEC 为主、自研 NLMS 兜底；`interruptLevel` 高 / 中 / 低三档灵敏度。

### 3.3 (c) 流式识别的改造：VAD 分段 + 云端分段识别 + LLM 整理

**问题**

- 硅基流动云端 ASR **不支持真正的流式**（主要为 HTTP 一次性提交，无 WebSocket 流式），因此 voco 目前识别有等待感
- 本地 zipformer2 流式识别**准确率不如云端大模型**
- 结论：**不走"本地识别 + 修正"路线**（本地识别不准）；**不放弃云端的高准确率**

**已验证的先例**

硅基流动生态里已有成熟案例——"说点啥"输入法（[BryceWG/BiBi-Keyboard](https://github.com/BryceWG/BiBi-Keyboard)）就是"语音识别 + AI 后处理"的组合，全用硅基流动免费模型：
- ASR：TeleSpeechASR / SenseVoiceSmall（也可用 Qwen3-Omni 多模态直接输入音频）
- 后处理：Qwen3-8B / GLM-4-9B

**方案（取两家之长）**

1. **本地 VAD 分段**（不做识别，只判断说话 / 停顿）
   - VAD 不需要"识别准"，它只判断你有没有在说话、一句话是否说完，本地做又快又准
   - 极轻量（Silero VAD 约 1.7MB，装 voice-mode 时已下载），无 API Key
2. **云端识别**：把当前累积的音频段提交硅基流动云端 ASR（详见下方"递增前缀提交"策略）
3. **LLM 整理重述**：全部说完后，用小模型（硅基流动免费的 Qwen / GLM）做一次整理
   - 修正识别错字、加标点、去掉"嗯 / 啊"等语气词、整理通顺
   - 可选：结合对话上下文补全指代（如"帮我看看它" → 重写为自包含的完整任务）

**核心设计：递增前缀提交（预览草稿 + 定稿）**

云端 ASR 不支持"增量拼接"，每次只能提交一段完整音频换整段文本，因此采用**递增前缀（滑动窗口）**模拟流式：

- 假设一句话共说 10 秒，本地 VAD 在说话过程中**周期性提交全部前缀**：前 2 秒 → 前 4 秒 → 前 6 秒 → 前 8 秒 → 完整的 10 秒
- 每次提交都能拿到一份"截至目前说得最全"的文本，用于**实时预览**（边说边出字的效果）
- **定稿原则**：前面所有提交都只是草稿预览，**以最后一次完整提交为唯一定稿**，一切以它为准；预览会被后续更全的提交覆盖，不影响最终质量
- 可视化示意（以 10 秒 / 5 次提交为例）：

  ```
  时间轴  0────2────4────6────8────10s
  提交1   [──2s──]        → 文本A（预览，草稿）
  提交2   [────4s────]    → 文本B（预览，覆盖A）
  提交3   [──────6s────]  → 文本C（预览，覆盖B）
  提交4   [────────8s────]→ 文本D（预览，覆盖C）
  提交5   [──────────10s─]→ 文本E（★定稿，交给 LLM 修正）
  ```

**关于截取位置的顾虑（已消解）**

- 若截取落在词中间（如"帮-我"之间），模型可能识别出奇怪的字——但这没关系：
  1. 下一次提交已包含更完整的音频，会覆盖掉错误预览
  2. 最后一次完整提交识别最准，是定稿依据
  3. LLM 修正再兜底清错别字
- **优化**：不要死板固定每 2 秒切一次，而是让本地 VAD 检测到"短停顿"（句子边界）就提交一次，截取位置大概率落在语义边界，预览更准、请求次数也更少；长停顿（约 1s+）视为句子结束，触发定稿

**延迟分析**

- 提交节奏约每 2 秒一次 → 第 2 秒的文本约在第 3 秒出头出现，用户已能实时看到 = 流式效果达成
- 比"等整段说完再识别"（10 秒末 + 识别耗时才出文本）快得多
- 额外的定稿延迟主要来自最后一步 LLM 修正：约 +1~2s，即说完后约 2~3 秒出定稿，可接受

**代价与优化**

- **冗余计算**：5 次提交等于处理约 30 秒音频量（实际只有 10 秒），云端免费额度消耗更快，需留意用量
- **LLM 修正只喂最后一段**：前几段是重复前缀，不必全丢给大模型；只把定稿文本交给 LLM，必要时结合上一段末尾做衔接，省 token、降延迟
- 拉大提交间隔（如 VAD 短停顿驱动而非固定 2s）可进一步减少请求次数与冗余

**热词表设计：解决专有名词 / 热词误修正**

**问题**：免费小模型没有学过 DeepSeek Harness、deep agents、LLM-Wiki 这类专有名词 / 新词，LLM 修正时可能按字面意思乱改（如把 "harness" 改成同音别的词）。

**核心原则：分层，词表不进提示词全量塞入**

- **规则层（绝大多数词表）**：纯本地代码做字符串 / 同音匹配替换（如识别出"迪普斯克哈纳斯"→ 规则表命中 → 替换回 "DeepSeek Harness"）。词表再大也不占模型上下文、无 token 成本，万级词条也无压力
- **提示词层（仅需裁决的少量候选）**：LLM 修正指令只声明一句原则"专有名词、英文术语、代码名一律不改"，不列词表；只有在规则层拿不准、需裁决时才把原文片段 + 3~5 个候选词喂给模型
- 职责切分：**规则层负责"改词"，LLM 只做"排版"**（加标点、去语气词、调通顺）——排版不需要知道热词，因此模型侧永远只处理一小撮需裁决的词，又快又稳又不爆上下文

**热词表维护（三部分）**

1. **内置基础包**：固定放入 DeepSeek Harness、deep agents、LLM-Wiki 等核心词
2. **用户自定义**：开放给用户自己加词
3. **自动积累**：从项目名、会话中反复出现的专有词、workspace 记忆自动收集，用一段时间表越来越懂用户

**补充**：需确认硅基流动 ASR 接口是否支持热词 / 自定义词汇参数——若支持，直接在识别层喂入热词，LLM 连见到错词的机会都没有，最省事。

**语音打断：复用增量识别做 barge-in 判定**

**现状**：voco 当前的打断逻辑是"识别到语音 + 语音转文本成功才打断"——可靠性够，但依赖整段完整识别，触发偏慢。

**核心思路**：增量识别上传的那 2 秒音频本就用于流式预览，可顺手复用它做打断判定——**识别出文本、确认是人在说话，才打断**，不增加任何额外上传。

- **防误伤**：狗叫 / 噪音虽然触发 VAD，但上传后 ASR 要么返回无意义音节、要么置信度低，判"不是人话"则不打断——这是"确认人声"比"有声就断"更稳的根本原因
- **触发延迟要调短**：打断不是 2 秒，而是 2 秒 + 上传 + 识别 + 网络往返（粗算约 3 秒），体感偏钝。优化：
  - 确认窗口压到约 1 秒（只需确认"在说话"，不必等完整句子）
  - 或两级配合：本地 VAD 做快速候选（一有声即预备），云端 ASR 确认一返回就打断——既快又不误伤
- **关键坑：回声自打断**。AI 朗读时麦克风会把扬声器里 AI 自己的声音也收进去，上传云端后 ASR 会把 AI 自己说的话识别成文本，导致 AI 打断自己的朗读（死循环）。**送云端前必须先做回声消除（AEC）**：拿正在播放的音频当参考信号，把 AI 自己的声音从麦克风信号中抠掉，剩下的才上传（参考 dsh-voice-mode：原生 AEC 为主 + 自研 NLMS 兜底）
- **离线兜底**：云端是打断的前提，断网时打断失效，需保留本地 VAD 快速兜底

**最终架构一句话**

> **云端模型负责"准" + 本地 VAD 负责"流式" + LLM 整理负责"顺"**，绕开本地识别不准的坑，兼顾准确率与流式体验。
