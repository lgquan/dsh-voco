## 问题描述

在 `frontend-agent` 语音模式下，第一次询问项目时能够正确委派后台 Agent 并读取项目资料，但后续追问项目规则、数字或实现细节时，前台路由有时会直接选择 `chat`。

这些回答没有重新读取项目文件，而是沿用最近对话、Workspace Memory 或模型已有知识。如果先前回答不准确，错误可能在连续追问中被继续放大，形成缺少事实依据的幻觉。

## 日志证据

目标语音会话中：

1. `seq=10`：用户提出“介绍一下这个项目吧”。
2. `seq=14`：创建后台任务 `2ed9ddb6-dd6e-4818-9bf9-e058b8a0ac19`。
3. 后台 Agent Session `session-996c9afb-6e39-4a70-8be6-ee84b7a14388` 的第 1 轮调用了 `pwsh`、`glob` 和 `read`，实际读取了项目目录及 `临床筛查PPT.md`。
4. `seq=26、30、34、38、42` 的后续项目追问之间，没有新的 `voice/task-delegated` 事件；后台 Agent 第 2 轮也没有 `tool/call`。
5. `seq=36、40、44` 的回答把“置信度修正”说成“根据规则命中结果调整”。
6. 用户在 `seq=46` 明确质疑后，`seq=47` 才再次创建后台任务；后台结果在 `seq=54` 纠正为“根据证据完整性和不确定表达调整”。

可以确认，这些错误回答没有经过新的项目文件读取，主要依赖已有对话上下文和前台模型生成。

## 影响

- 项目事实、实现细节、数字和文档口径可能被当成普通闲聊处理。
- 前台模型可能复述或放大上一轮回答中的错误，而不是回到项目资料核对。
- 用户无法从语音表现判断回答是否经过项目文件验证。
- 需要可追溯、可复核的项目介绍和面试准备场景会受到明显影响。

## 原因判断

原路由提示词允许“无需外部事实或工具即可可靠回答的稳定知识”选择 `chat`。路由模型可能把连续项目追问误判成基于上下文的自然聊天；一旦选择 `chat`，代码会直接播报模型生成的 `reply`，不会创建后台任务或读取文件。

最近语音对话和 Workspace Memory 都只能作为上下文或历史参考，不等同于重新读取当前项目文件，也不能作为项目事实的最终权威来源。

## 解决方案

### 1. 背景

`frontend-agent` 语音模式目前会把用户转写交给前台路由模型，由模型选择 `chat`、轻量 `tool` 或后台 `delegate`。

当前链路已经支持 Workspace Memory，但项目事实类追问可能被误判为普通上下文聊天。此时前台模型会沿用上一轮助手回答，而不是重新读取项目文件，可能导致事实错误被继续放大。

典型表现是：第一次介绍项目时委派后台 Agent 并读取文档；后续追问具体规则、数字或实现细节时直接 `chat`，没有新的文件读取；用户质疑后才委派后台任务并纠正答案。

### 2. 目标与非目标

#### 目标

- 项目事实问题优先获得项目文件依据。
- 保留自然、低延迟的普通语音聊天体验。
- 保留后台 Agent 对搜索、执行和文件修改任务的能力。
- 让“检索不到可靠依据”成为明确状态，禁止模型假装有依据。
- 保留现有后台任务、结果改写和 TTS 链路。
- 为回答提供可追溯的文件路径和行号信息。

#### 非目标

- 不把每一句语音都委派给后台 Agent。
- 不把 `frontend-agent` 改造成 `speech-shell`。
- 不让路由模型自行调用 `glob/read` 并重建工具调用循环。
- 第一版不引入向量数据库、复杂语义检索或关键词生成 LLM。

### 3. 总体方案

保留现有路由层，在路由模型调用前增加一个受控的项目事实预检索步骤。

```text
语音输入
  ↓
Workspace Memory recall
  ↓
确定性 grounding 信号检测
  ↓
命中项目事实信号时执行受控本地预检索
  ↓
组合最近对话、Workspace Memory、项目片段和 grounding 状态
  ↓
前台路由模型
  ├─ 有可靠依据的解释类问题 → grounded chat
  ├─ 本地依据不足 → delegate
  ├─ 需要网络搜索 → delegate
  ├─ 需要执行或修改 → delegate
  └─ 普通聊天 → chat
  ↓
插件侧确定性兜底校验
  ↓
现有后台 Agent、结果改写和 TTS
```

`groundingRequired` 表示“必须基于可靠依据处理”，不直接等同于“必须委派”。只有证据达到 `found-sufficient` 时才允许前台自然回答；证据不足、未命中或检索失败时，必须委派后台 Agent。

### 4. 触发策略

#### 4.1 确定性 grounding 信号

第一版由插件代码检测，不增加额外 LLM 调用。信号包括：

- 项目指代：`这个项目`、`项目里`、`我们系统`、`当前项目`；
- 资料指代：`文档`、`PPT`、`讲稿`、`资料里`、`按文件`、`按项目资料`；
- 实现指代：`代码怎么做`、`具体实现`、`源码`、`规则链`、`几层`、`具体数字`；
- 核对/纠错：`你刚才说得对吗`、`重新确认`、`核对一下`、`是不是说错了`、`以文档为准`；
- 当前回答明显依赖项目专有名词或文件名。

命中信号只触发 grounded 路径和本地预检索，不直接强制后台委派。

#### 4.2 不触发预检索的情况

- 普通寒暄和日常对话；
- 纯粹的语气衔接；
- 不增加新事实、只是复述刚刚已经核对过的内容；
- 明确要求执行命令、修改文件等动作任务，此类请求直接由路由判断为 `delegate`，不需要先做完整本地检索。

### 5. 分层证据检索与缓存

项目事实的检索来源不只有原始文件。语音改写可能压缩掉 Agent 已经读取和综合出的细节，因此应将这些结果纳入统一的分层证据检索体系。

#### 5.1 来源与权威等级

| 来源 | 角色 | 权威级别 |
| --- | --- | --- |
| 当前版本的项目文件 | 新鲜事实源 | 最高 |
| 项目文件片段缓存 | 文件检索结果缓存 | 高 |
| Agent 完整 `voice/task-observation.detail` | 已完成任务的综合结果缓存 | 中高 |
| Workspace Memory 摘要 | 长期语义记忆 | 中低 |
| 最近语音对话 | 会话上下文 | 较低 |

Agent 的 `detail` 首先是持久化任务结果，不应未经标记直接当作当前事实。只有建立索引并记录来源、新鲜度和版本后，才允许作为候选证据参与检索。

推荐的权威排序是：

```text
当前版本项目文件
  > 与当前文件版本匹配的 Agent detail
  > 文件版本未知或已过期的 Agent detail
  > Workspace Memory 摘要
  > 普通对话上下文
```

#### 5.2 证据缓存条目

```ts
type EvidenceCacheEntry = {
  workspacePath: string
  queryKey: string
  sourceType: 'file' | 'task-detail' | 'workspace-memory'
  content: string
  sources: Array<{
    path?: string
    startLine?: number
    endLine?: number
  }>
  createdAt: string
  sourceVersion?: string
  freshness: 'fresh' | 'stale' | 'unknown'
  confidence: 'sufficient' | 'insufficient' | 'unknown'
}
```

缓存条目必须能回答四个问题：来自哪里、对应哪个工作区、是否仍然新鲜、是否足以支撑当前回答。来源路径和行号应保留在页面或日志中，不直接放进 TTS 文本。

#### 5.3 检索顺序

命中 `groundingRequired` 后，按以下顺序召回：

1. 当前工作区的文件片段缓存或受控本地检索；
2. 同一工作区内、来源版本匹配的 Agent `detail`；
3. 版本未知或已过期的 Agent `detail`，只能作为参考；
4. Workspace Memory；
5. 最近语音对话，仅用于消歧，不作为项目事实的最终依据。

如果新鲜文件片段已经足够，不需要读取旧的 Agent 结果；如果只有旧结果或记忆摘要，路由必须将证据标记为不足或过期，并委派后台 Agent 重新验证。

#### 5.4 Agent 结果的复用

- 完整 `detail` 保留在持久化 `voice/task-observation` 事件中；
- 本轮为 `detail` 建立按工作区、任务编号和事件时间的进程内检索索引；
- 当前事件结构没有独立的来源文件和文件版本字段，因此 `detail` 一律标记为历史候选，不宣称与当前文件版本一致；
- `detail` 只作为定位提示或候选证据，后台重新读取的结果才是最终权威；
- 当前文件片段已经充分时，不再向路由注入旧 `detail`；只有当前文件依据不足时才使用它辅助定位；
- 错误、取消或未完成的任务结果不进入可用证据缓存；
- 语音改写后的短文本不作为完整事实缓存，避免把压缩结果再次当作原始依据。

### 6. 受控本地检索适配层

#### 6.1 输入与输出

输入：

- 当前 Session 的工作区路径；
- 用户原始转写；
- 受限关键词或项目术语。

输出：

```ts
type WorkspaceEvidence = {
  status: 'found-sufficient' | 'found-insufficient' | 'not-found' | 'error'
  matches: Array<{
    path: string
    startLine: number
    endLine: number
    text: string
  }>
  truncated: boolean
  message?: string
}
```

#### 6.2 第一版检索方式

- 关键词直接来自用户转写和确定性术语表；
- 优先匹配文件名，再匹配文件内容；
- 优先检索 Markdown、TypeScript、JavaScript、JSON、YAML 等文本文件；
- 返回有限数量的命中片段，而不是读取整个项目；
- 每个片段必须带相对文件路径和起止行号；
- 命中片段不足以支撑回答时返回 `found-insufficient`，不能因为“有一点命中”就允许模型直接回答；
- 没有命中时返回明确的 `not-found`，不能返回空字符串让模型自行猜测；
- `error` 和 `truncated` 都不能被当成可靠事实依据。

第一版暂不使用向量检索、同义词生成模型或额外关键词生成 LLM。后续只有在真实回放显示词法检索遗漏明显时，再增加术语索引或语义检索。

#### 6.3 资源与安全限制

适配层必须是受控只读能力，不能简单地对任意路径调用 `readFile`：

- 只允许访问当前 Session 工作区；
- 防止路径穿越和符号链接逃逸；
- 忽略 `.git`、`node_modules`、构建输出和缓存目录；
- 限制允许的文件扩展名；
- 限制命中文件数量、单片段大小和总返回字节数；
- 设置检索超时；
- 不执行文件内容中的命令或脚本；
- 使用宿主进程已有的操作系统读取权限，不扩大到当前 Session 工作区之外；
- 对 `error` 和 `truncated` 状态写入可观测日志。

当前 DSH 文件工具没有可供插件复用的 `glob/grep` 接口，因此本轮采用插件内最小只读适配层。适配层在读取前解析真实路径并再次确认其位于工作区内，跳过符号链接、敏感文件名和受限目录。该预检索不进入 DSH 工具审批链，这是当前接口条件下的已知边界；未来 DSH 提供带审计的只读搜索服务后，应迁移到该服务。

#### 6.4 检索结果缓存实现

连续语音追问可以复用短期检索结果，但缓存不能无限期保留：

- 缓存键至少包含工作区路径、关键词集合和检索配置版本；
- 对全部可检索文件的相对路径、修改时间和大小生成工作区版本指纹；
- 默认 TTL 为 10 分钟，最多保留 64 条；任何可检索文件新增、删除、修改或移动时，即使仍在 TTL 内也立即失效；
- 工作区切换、文件版本变化或检索配置变化时立即失效；
- 扫描超时或结果截断时不写入缓存；
- `error` 结果不应长期缓存；
- 缓存只用于减少重复定位，不能替代后台 Agent 对原文件的最终验证。

### 7. 路由提示词约束

路由模型继续只输出现有三类结构，但增加以下上下文：

- `groundingRequired: true | false`；
- `workspaceEvidence.status`；
- 带来源标记的项目文件片段；
- 检索是否截断。

核心约束：

1. `groundingRequired=true` 时，项目事实回答只能基于注入的项目片段和明确的对话事实。
2. `workspaceEvidence.status` 为 `found-insufficient`、`not-found` 或 `error` 时，不得选择普通 `chat` 编造项目事实，应选择 `delegate`。
3. 最近助手回答只是上下文，不是项目事实来源；需要核对时必须回到项目片段或后台 Agent。
4. 有项目片段但用户要求修改、运行、搜索或其他动作时，仍然选择 `delegate`。
5. 网络搜索和工作区执行不由前台路由直接完成，统一委派后台 Agent。
6. 路由模型可以看到来源路径和行号，但 `chat` 的语音文本只输出自然口语，不朗读路径、行号、检索过程或内部路由字段。

### 8. 插件侧确定性兜底

路由模型输出解析后增加硬性校验，且必须在任何语音输出之前执行：

```text
groundingRequired=true
且 evidence.status != found-sufficient
且 route.action == chat
→ 在 speak 之前覆盖为 delegate
```

同样，以下情况无论模型输出什么都必须委派：

- 用户要求创建、修改、删除、重命名或移动文件；
- 用户要求运行命令、测试、安装依赖或执行外部搜索；
- 检索状态为 `error` 或 `found-insufficient`；
- 用户明确要求核对原始资料而当前片段不足。

这层兜底的目的是防止模型自评“信息够了”时越过事实边界。当前代码中 `chat` 会直接调用 `speakFragment(route.reply)`，所以兜底校验的落点必须是：

```text
routeFrontendInput()
  → grounding / action 硬校验
  → 通过后才允许 speakFragment()
```

### 9. 后台委派与结果播报

后台 Agent 仍然是执行和权威验证主体。

- 前置检索片段可以作为后台任务的定位提示；
- 片段不是最终权威，后台 Agent 仍需读取和验证原文件；
- 后台任务继续使用现有 `task`、`background` 和 `user_request` 结构；
- 现有简短 acknowledgement、任务观察、结果改写和 TTS 不变；
- 语音不直接朗读完整文档，最终只播报适合语音的摘要；
- 页面或日志可以保留完整回答和来源信息；
- 来源路径、行号等结构化证据不通过语音文本传递，避免 TTS 读出内部检索细节。

### 10. 兼容性与成本

#### 普通聊天

不命中 grounding 信号时不做项目文件预检索，保持当前一次路由调用和低延迟体验。

#### 项目事实问答

增加一次有上限的本地预检索，但避免完整扫描。只有证据状态为 `found-sufficient` 时，前台才可以直接生成简短回答；“少量命中”或片段被截断时仍应委派。

#### 委派任务

如果预检索没有足够依据再委派，后台 Agent 仍需验证文件。后续可以评估是否把已命中的片段作为提示传入，减少重复定位，但不能牺牲后台验证。

#### 网络和执行任务

仍然直接委派后台 Agent，不试图用本地检索替代网络搜索或动作执行。

### 11. 实施顺序

1. 抽取 `groundingRequired` 信号检测函数和测试表。
2. 确认工作区路径来源和当前权限/沙箱可复用接口。
3. 实现受控只读本地检索适配层。
4. 增加有界的会话内检索缓存和文件版本失效判断。
5. 将证据状态、片段和来源标记注入路由提示词。
6. 增加路由结果的确定性 grounding 兜底校验，并放在 `speak` 之前。
7. 保持后台委派、结果改写和 TTS 链路不变。
8. 增加单元测试、路由回放测试和真实语音回归测试。

### 12. 验证计划

#### 必测项目事实问题

- “这个项目的规则链有几层？”
- “PPT 里是怎么写的？”
- “你刚才说的置信度修正准确吗？”
- “按项目资料重新确认一下。”

检查：是否触发 grounding、证据状态是否正确、是否带路径和行号、无命中或证据不足时是否委派，以及委派发生前是否没有提前播报错误的 chat 回复。

#### 必测普通对话

- “你好。”
- “继续说。”
- “明白了。”

检查：不触发完整文件检索，不被强制委派，回复仍然自然简短。

#### 必测动作任务

- “帮我修改这个文件。”
- “运行一下测试。”
- “去网上查一下最新信息。”

检查：始终委派后台 Agent，不因本地命中片段而误走 `chat`。

#### 必测硬兜底

- 模拟路由模型在 `groundingRequired=true` 且 `found-insufficient` 时错误返回 `chat`；
- 断言插件在 `speakFragment()` 之前将其覆盖为 `delegate`；
- 断言没有产生错误的语音输出；
- 模拟检索 `error`、超时和截断，确认都不会放行普通 `chat`。

#### 观测指标

- 项目事实问题的 grounding 触发率；
- 后台委派率；
- 后台实际文件读取率；
- 未委派事实错误率；
- 普通闲聊误触发率；
- 检索耗时和整体语音延迟；
- 检索命中率、截断率和错误率。
- 缓存命中率、缓存失效率和文件版本变更后的新鲜度。

### 13. 验收标准

- 项目事实问题没有可靠本地依据或证据不足时，不允许前台直接编造回答；
- 有可靠片段的只读解释类问题可以自然 `chat`；
- 修改、执行、网络搜索类请求仍然稳定 `delegate`；
- 普通聊天的延迟和交互方式不发生明显退化；
- 检索片段带可定位的文件路径和行号；
- 结构化来源信息可保留在页面或日志中，但不会被 TTS 直接读出；
- 文件检索不越过工作区和 DSH 权限边界；
- grounding 兜底发生在 `speak` 之前；
- “置信度修正”错误案例回放时，能够触发 grounded 路径并得到项目文档支持的回答。
